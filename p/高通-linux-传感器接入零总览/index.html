高通 Linux 传感器接入（零）：总览

第零篇目标是建立整体结构。把 SLPI、QMI、QRTR、FastRPC、hexagonrpcd、libssc、iio-sensor-proxy 按层次和职责区分清楚，重点说明两条通路：传感器数据/控制通路，以及固件/配置辅助通路。

Sep 17, 2026
阅读时长: 2 分钟

缘起

笔者购入Matepad ego 2023（代号gaokun3）后，便跃跃欲试地尝试参与进Ubuntu移植工作，积累Linux开发经验，我查看已经编译出可用镜像的仓库的上游补丁仓库，想要从其中寻找到一些我好入手1，不涉及太多Linux核心知识的，同时能让使用体验向Windows对齐的待移植功能时，我一眼就相中了传感器，他有着能跑通但是不完全跑通的现况，自动旋转，自动亮度功能等也依附于传感器驱动，若是能移植成功，那能极高的提高使用体验（棒读）。但随着移植的深入，我不得不阅读浩如烟海的英文文献，从琐碎的内核邮件列表中寻找蛛丝马迹，运用AI阅读并总结相关支持库的使用方式，最终成功读取到了加速度，陀螺仪与光照传感器的数值，并且使用了校准矩阵。中文社区缺少成体系的高通 Linux 传感器接入的经验文章，于是诞生了这系列文章

两个通路

传感器数据侧 物理传感器 → SLPI → QMI/QRTR → libssc → iio-sensor-proxy → D-Bus

数据侧负责把物理传感器的测量值送到 Linux 用户态，并最终通过 D-Bus 提供给桌面和应用。这条通路同时承载下行控制（使能、采样率、批处理）和上行数据（测量值、事件）

传感器固件侧 SLPI ↔ FastRPC ↔ hexagonrpcd

让 SLPI 上的传感器固件能够访问主机 Linux 文件系统，加载配置、校准、注册等文件，从而完成初始化和 Sensor Manager 注册

两个通路组合起来，形成了完整的读取链路

组件职责

传感器数据链

SLPI

SLPI 是高通 SoC 中一个独立的 DSP 子系统23，负责管理连接到 SoC 的物理传感器。它的核心设计目标是在主 CPU（AP）休眠时，仍能低功耗地维持传感器数据采集和事件监测。对于 Linux 开发者，最关键的一点是：在 SLPI 架构下，AP 无法直接访问传感器。传感器虽然物理上连接在 SoC 的 GPIO 上，但 Hypervisor4 会阻止 AP 的直接访问，因此任何传感器操作都必须通过 SLPI 这个“代理”来完成。SLPI 启动后，会通过 QRTR 总线对外暴露 service 400，即 Sensor Manager 服务。 SLPI 通过内核的 remoteproc5 框架启动，具体由 qcom_q6v5_pas 驱动完成固件加载

QRTR与QMI

QRTR6 是高通 SoC 内部的 IPC（进程间通信）路由器协议，为芯片上不同处理器（AP、SLPI、ADSP、Modem 等）之间提供寻址和消息传输服务 QMI7 服务是高通芯片内部，不同处理器（如主 CPU 和 DSP）上运行的软件模块之间，基于 QMI 协议进行通信的一个逻辑实体。 它遵循客户端-服务器模型，一个服务可以被其他处理器上的客户端调用。

两者之间的关系：

  • 每个处理器（如 AP、SLPI）都有独立的 QRTR 地址。
  • 每个 QMI 服务（如 Sensor Manager）在 QRTR 上有自己的端口号（如 service 400）。
  • 客户端通过 QRTR 地址 + 端口号找到目标服务，发送 QMI 消息。

主线内核正在推进将 QRTR 从纯网络协议改造为一条总线（bus），让 QMI 服务能够像设备一样被内核动态探测8

libqmi 与 libssc

libqmi9 是 QMI 协议本身的用户态实现，它把 QMI 消息与底层传输解耦；QRTR 只是它支持的传输后端之一，在 1.34.0 版本（2023 年 10 月发布）新增了 SSC（Qualcomm Snapdragon Sensor Core）服务，包括 Control 请求/响应和 Report Small/Report Large 指示 libssc10 基于libqmi，在 Linux 用户态与 SLPI 上的 Sensor Manager QMI 服务之间建立通信，将传感器数据以标准的 GLib API 形式暴露给上层应用。 它的功能有：

  1. QMI 消息构造与解析：为 Sensor Manager 服务（sns_client_api_v01）构建 QMI 请求，并解析响应中的 Protobuf 编码数据。
  2. 传感器枚举与发现：启动时向 SLPI 查询可用传感器列表。
  3. 数据订阅与回调：向上层提供异步回调机制，传感器数据到达时触发事件，避免应用轮询。
  4. GLib 集成：基于 GLib 的事件循环和对象模型，便于与 iio-sensor-proxy 等使用 GLib 的守护进程集成。

iio-sensor-proxy

iio-sensor-proxy11 是用户态数据通路中最终面向桌面环境与应用的守护进程。它的作用是把底层传感器数据统一封装成 D-Bus 接口，让桌面环境、应用程序和上层框架无需关心传感器来自哪里、走的是哪条路径。

传感器固件链

FastRPC

FastRPC 是高通 SoC 中 DSP 与主机 Linux 之间的远程过程调用机制。它允许运行在 SLPI（或其他 DSP）上的固件代码，调用主机用户态进程提供的服务，最典型的就是从主机文件系统读取文件。如：

  • 传感器配置文件（JSON、文本等）
  • 传感器校准数据
  • 传感器注册文件（Sensor Registry 相关）
  • 固件运行所需的其他资源 这些文件不在 SLPI 本地，而是在主机 Linux 文件系统上。SLPI 固件无法直接访问主机文件系统，因此需要一种机制：让 DSP 能够向主机发起文件操作请求，由主机用户态进程代为执行。

hexagonrpcd

hexagonrpcd12 是高通 Linux 传感器架构中，运行在主机用户态、配合 FastRPC 为 SLPI 固件提供文件访问服务的守护进程。它属于固件/配置辅助通路，不传输传感器数据本身，但它的正常工作，是 Sensor Manager 在 QRTR 上就绪和数据通路打通的前提。 hexagonrppcd开始被设计为只能读取文件，但是最近有关修改，新建文件的功能实现正在逐渐合并，此举能改善缺少配置文件的项目启动SLPI带来的崩溃。

remoteproc

remoteproc 是 Linux 内核中用于加载远程处理器（Remote Processor）固件并管理其生命周期的框架。在高通 SLPI 传感器架构中，它正是负责启动 SLPI DSP 的那一环。
